# Expose callable applicability and overload selection evidence to RQL/RQLP (issue #1478)

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agents/PLANS.md` at the repository root.

Parent context: this is child issue #1478 of epic #1472, which turns 275 mined Bifrost bug-fix commits into typed RQL/RQLP capabilities. This slice owns structured call shapes, callable signatures, call-site-to-candidate applicability, and overload selection evidence. Sibling #1477 owns receiver evidence, member-candidate enumeration, hierarchy routes, and dispatch tiers; its plan records `callable_applicability_deferred` for a candidate that loses only because of call arguments, and this plan replaces that deferral with a real applicability row. Sibling #1475 owns canonical identity through aliases and indirection; this plan uses exact analyzer `CodeUnit` identity. Sibling #1473 landed content-scoped occurrence rows, stable AST IDs, and resolver-owned `TraceCandidate` rows; this plan correlates through those IDs and enriches that trace instead of recording candidates a second time.

## Purpose / Big Picture

Bifrost's language resolvers already discriminate overloads: Java filters constructor candidates by arity (`java_filter_candidates_by_arity` in `crates/bifrost-analysis/src/analyzer/usages/get_definition/java.rs`), C++ matches call shapes in `crates/bifrost-analysis/src/analyzer/usages/cpp_call_match.rs`, C persists variadic callable arity, Scala matches curried and contextual argument lists, and C# models callable applicability. Every one of those checks computes an answer and throws the evidence away. The public result exposes only the winner, so RQLP cannot state the invariant that motivated the 31 mined bug-fix commits: for this exact ordered call shape, these are all callable candidates, this candidate is applicable and uniquely selected, zero applicable candidates stay unresolved, and several equally applicable candidates stay honestly ambiguous rather than being broken by candidate order.

After this plan is complete, an RQLP assertion can bind call occurrences, expand each into one mandatory call-shape outcome row plus ordered argument-list-group and argument rows, expand candidate callables into signature rows carrying required/total/repeated arity, list kinds, parameter names, generic arity, receiver contract, return type, and declaration role, join call sites to per-candidate applicability rows carrying substitutions, an accepted or structured rejected reason, precedence tier, proof, and completeness, and assert that the selected target sits in the winning applicability tier with exactly zero, one, or many winners. A macro-expanded or configuration-derived argument list that the analyzer cannot see produces an incomplete call-shape outcome, and any exact-cardinality assertion over it is `unreliable`, never clean.

The behavior is visible through `query_code` JSON/RQL result rows and through `run_policy`. For a seeded wrong-overload resolution, an invariant policy reports one multi-location finding containing the call site, the selected callable, and the applicable competitor; the corrected fixture is clean; a macro-derived call shape is `unreliable`.

- Observation: `CallableArity { required, total, repeated }` already exists in `crates/bifrost-core/src/analyzer/model.rs` with an `accepts(arity)` predicate, and `SignatureMetadata` already persists parameter labels with byte ranges, type parameters, and an extension-receiver flag. ## Decision Log

- Decision: reuse the production per-language call matchers as the single applicability source; never build a shared overload-resolution algorithm in the query layer.
  Rationale: the 31 commits show applicability is language semantics (Scala curried/contextual lists, C variadics, C++ template aliases, C# named arguments). A query-side solver would be a second resolver, which the epic prohibits. Each language adapter factors its existing check so the get-definition result and the applicability row come from one function.
  Date/Author: 2026-08-06 / Claude.
- Decision: model a call shape as one mandatory outcome row plus ordered argument-list-group rows plus ordered argument rows, all with stable IDs and foreign keys, rather than one flat arity integer.
  Rationale: the issue's rule contract requires list kinds, arity ranges, generic/type arguments, named/contextual arguments, receiver binding, and call role. Same-total-arity/different-list-shape overloads are a required fixture; a flat count cannot distinguish them.
  Date/Author: 2026-08-06 / Claude.
- Decision: put the constrained call-shape/applicability vocabulary (argument-list kinds, call kinds, applicability verdicts, callable rejection reasons) in `crates/bifrost-core/src/analyzer/structural/` beside `resolution.rs`, using the existing `labelled_enum!` pattern; keep row production and CodeQuery registration in `brokk-bifrost-analysis`; keep relational predicates in `brokk-bifrost-policy`.
  Rationale: the vocabulary is dependency-bottom model data shared by the persisted signature contract and by forward/inverse/cold/warm consumers; core must not depend on other Bifrost crates, and analysis-side code needs `IAnalyzer`.
  Date/Author: 2026-08-06 / Claude.
- Decision: extend candidate rejection with a separate `CallableRejectionReason` constrained enum carried by applicability rows, instead of widening the landed `RejectionReason`.
  Rationale: `RejectionReason` names scope/visibility/namespace checks shared by all reference resolution; callable applicability is a different axis that applies only to call-shaped occurrences, and #1477's member candidate rows already reference the existing enum. A distinct enum keeps both vocabularies exhaustive without a grab-bag variant.
  Date/Author: 2026-08-06 / Claude.
- Decision: candidate order is never a semantic tie breaker. When more than one candidate is applicable in the winning precedence tier, the selection outcome is `ambiguous` with all winners retained; when zero are applicable, the outcome is `unresolved` with all rejected rows retained.
  Rationale: this is the issue's rule contract verbatim, and it is the invariant the seeded-bad fixture must be able to catch.
  Date/Author: 2026-08-06 / Claude.
- Decision: unknown macro- or configuration-derived call shapes produce a mandatory outcome row with incomplete/unknown shape coverage and no fabricated argument rows.
  Rationale: commit `a87b3904f` (macro-expanded C/C++ call arity) shows shapes the analyzer cannot always see. Exact-cardinality assertions over incomplete shapes must be `unreliable`, never clean, matching the epic's fail-unreliable contract.
  Date/Author: 2026-08-06 / Claude.
- Decision: derive the first call-shape slice from the shared facts arena (`NormalizedKind::Call` with `Role::Arg`/`Role::Kwarg`/`Role::Receiver`, spread flags, and keyword spans), not from fresh tree-sitter walks. The arena models one positional group and one named group today, so the slice emits at most `Ordinary` then `Named` groups and classifies only `Function` versus `Method`; a call with zero positional arguments still gets one empty `Ordinary` group, while the `Named` group is omitted when absent. Constructor/extractor/infix/method-value kinds and curried/contextual/block/type-argument groups arrive with per-language enrichment and are never inferred from source text. Two interface deltas from the original sketch: `ArgumentRow` carries a per-argument `spread` flag (the arena records spread per argument, and a whole-group `VariadicPack` kind would erase mixed lists like `f(a, *rest)`), and `CallShapeOutcome` carries a non-optional `site_ast_id` plus an optional `callee_range` (the exact facts node is always known here, unlike receiver sites; a callable-object call has no callee token).
  Rationale: one structured source that get-definition already trusts, no re-parsing, and honest coverage for what the arena cannot express yet.
  Date/Author: 2026-08-06 / Claude.
- Decision: carry per-language call-site classification in the fact arena, filled at extraction time through two new `StructuralSpec` methods (`call_site_context` once per file, `call_site_facts` per call node), rather than re-parsing at derivation time or switching on language inside the shared derivation module.
  Rationale: the distinctions this milestone needs - constructor versus ordinary application, infix versus symbolic operator, one call site versus one more argument list of a curried application, readable versus macro-derived argument list - are all readable from the grammar node and from nowhere else once the tree is dropped. The derivation layer never sees a tree, and a language switch inside it would put language semantics in the shared module. The classification is optional per language: an adapter that says nothing keeps the receiver-derived baseline, which is the honest answer rather than an approximation. The cost is one arena field and structural snapshot version 7, which is an ordinary cache miss.
  Date/Author: 2026-08-11 / Claude.
- Decision: an argument list whose coverage is not `Exact` emits zero group rows and zero argument rows.
  Rationale: a fabricated empty `Ordinary` group would be byte-identical to a real zero-argument call, which is exactly the confusion the coverage field exists to prevent, and it would let an exact-cardinality assertion over a macro-derived site read as clean.
  Date/Author: 2026-08-11 / Claude.
- Decision: a signature row's identity is anchored on the declaration *site* (file, fully qualified name, byte range), not on the canonical member digest that member-family rows use.
  Rationale: an overload set is exactly the case this milestone exists to make queryable, and its members share a canonical member identity by design. Anchoring there gave both overloads one row id, which the pipeline's key-based deduplication then collapsed into a single row. The declaration site is the finest identity the row actually describes.
  Date/Author: 2026-08-11 / Claude.
- Decision: report a receiver contract only when the persisted facts decide it, and no contract at all when the adapter never inspected modifiers.
  Rationale: "not recorded static" and "nobody read the modifiers" are different answers, and only an extension receiver and a constructor are decidable without modifiers. Publishing `instance` from ownership alone would let a policy state a contract the analyzer never proved. Where the gap was worth closing, it was closed at the source: C# now records its modifiers.
  Date/Author: 2026-08-11 / Claude.
- Decision: leave curried and contextual parameter-*list* segmentation out of Milestone 2 and state the gap, rather than recovering it from the rendered signature label.
  Rationale: no persisted structure carries the list boundaries, so the only available recovery is delimiter scanning of a rendered header -- prohibited, and wrong for any language whose header rendering differs from its source. Representing it honestly means adding a persisted `SignatureMetadata` field and bumping every language epoch (the blob is bincode, so a layout change invalidates every language's rows, not only the ones that fill the new field). That is its own change with its own blast radius, and Milestone 2's other acceptance criteria do not depend on it: an overload set at equal total arity is already separable by its declared parameter rows.
  Date/Author: 2026-08-11 / Claude.
- Decision: carry callable applicability on its own `TraceCandidate` field (`callable`), separate from #1477's `MemberEnrichment.applicability`, and declare language support through a new `EnvironmentAxis::CallableApplicability` that starts unsupported for every adapter.
  Rationale: the member axis and the callable axis answer different questions and are recorded at different seams -- a constructor call has no member walk and still has an applicability answer. A shared axis would have forced every callable seam through a member record it does not have. Declaring support per adapter through the existing axis table means there is no default `supported`: a language reaches these rows only after its own check has been factored, and until then its sites honestly report `unknown_shape`.
  Date/Author: 2026-08-11 / Claude.
- Decision: the selection summary is computed from verdict counts and does not re-derive the site's call-shape coverage.
  Rationale: counts are order-independent by construction, which is the issue's contract rule stated as code rather than as a test. Coverage already exists as the `call_shape` row's field, joined on the same `site_ast_id`; a second derivation here could drift from the first, and the milestone's whole premise is that one answer must have one source.
  Date/Author: 2026-08-11 / Claude.
- Decision: publish a callable record only where the site actually writes an argument list, and leave a bare-term reference unattributed on the callable axis.
  Rationale: Scala's filter also runs over sites with no call shape at all, where it decides on declaration space alone -- a constructor is not an ordinary call target. That refusal is real and keeps its `wrong_declaration_space` reason on the resolution axis, but nothing about a call's argument lists was measured, so stating a callable verdict there would publish a check nobody ran. Absent is the honest answer, and the selection summary already turns any absent verdict into `unknown_shape`.
  Date/Author: 2026-08-11 / Claude.
- Decision: leave generic substitutions out of the applicability row and state the gap.
  Rationale: no language resolver records a structured substitution map at its applicability check today. An empty substitutions list would read as "no substitutions were needed", which is a claim nobody proved. Adding one is a resolver-side addition per language, not a derivation -- the same stance Milestone 2 took on parameter-list segmentation.
  Date/Author: 2026-08-11 / Claude.
- Decision: `ordered-equal` is an aggregate operation, not a new assertion record, and it yields one or zero rather than a count of disagreeing positions.
  Rationale: an aggregate reuses the group, the `:where` filter, the cardinality assertion, the finding anchor and the representative rows exactly as they are, so the ordered predicate needs no second reporting path. Yielding one for parity keeps the record readable as what it asserts -- `(exactly 1)` says "these lists are equal" -- where a disagreement count would have to be asserted `(exactly 0)` under a name that says `equal`. The count of disagreeing positions would be better diagnostics, but a violation already retains its contributing rows, which point at the exact positions.
  Date/Author: 2026-08-11 / Claude.
- Decision: `assert-selected-in-winning-tier` lowers at decode time into join/group/aggregate/assert records and adds nothing to the evaluator.
  Rationale: the milestone forbids new evaluator machinery where lowering suffices, and lowering has a stronger property than economy: the sugar cannot mean anything the same author could not have written by hand, so its findings, evidence, representatives and completeness gating are the ones the relational path already proves. The emitted group and aggregate are named after the assertion id, so a hand-written record of the same name collides and is reported as a duplicate rather than silently sharing a group, and the emitted join is appended after every authored join so the sugar can only extend a tuple set the author already connected.
  Date/Author: 2026-08-11 / Claude.
- Decision: an ordered sequence whose position column is absent at some row, or whose rows claim one position with different values, is undefined, and an undefined sequence is never parity.
  Rationale: the alternative -- picking one of the conflicting values, or skipping the row -- would report parity over a sequence nobody can reconstruct. Zero is the honest answer, and it is the answer that fails an `(exactly 1)` parity assertion rather than passing it.
  Date/Author: 2026-08-11 / Claude.
- Decision: no new `RowExpansionStep` values for the call-shape, signature and applicability domains; a policy binds them as inline RQL queries.
  Rationale: every one of those row domains already has a registered RQL wrapper form from Milestones 1 through 3, so `(bind :name c :query (rql (callable-applicability (occurrences ...))))` reaches them today with no new vocabulary at all. An expansion step is worth minting when it removes an otherwise unwritable query, not when it renames one; adding seven of them would have widened the policy vocabulary, the canonical form and the evaluator's step table for an ergonomic alias.

## Outcomes & Retrospective

Milestone 1 is behaviorally complete for what the shared structural lowering can express. An RQL author can bind call occurrences and expand them into one mandatory call-shape outcome row plus ordered argument-group and argument rows, across Java, Scala, C#, C++, TypeScript, and Python, and can tell a zero-argument call from a call whose argument list the analyzer cannot read. Evidence: `cargo test --test suite_cross_language code_query_call_shape_languages` (7 passed) and the unit tests in `crates/bifrost-analysis/src/analyzer/usages/call_shape.rs` (11 passed).

The capability gaps are stated rather than approximated, and each is a lowering gap, not a derivation gap: there is no contextual (`using`), block, or type-argument group anywhere, because no adapter records one; there is no Scala constructor call site, because Scala's `instance_expression` is not a call fact; there is no extractor kind; and C/C++ macro detection sees only macros defined in the same translation unit, not ones from an included header. Milestones 2 through 6 remain unstarted.

The design lesson worth carrying forward: the derivation layer never sees a tree, so anything that needs grammar structure has to be decided during extraction and carried on the arena. Adding an optional per-node classification with a per-file context hook cost one arena field and one snapshot version, and it keeps every language's answer opt-in, which is what let four languages be enriched without any other language claiming a refinement nobody implemented.

Milestone 3 is complete. Every language whose resolver performs an argument-shape check reports per-candidate applicability from the same function that computes its winners -- Java, Kotlin, Scala, C, C++ and C# -- and the rows are queryable through `callable-applicability` and `overload-selection` for Java, the one language that classifies `member_position` occurrences today. The other five are pinned at the production trace, which is where their #1477 rows are pinned too; closing that is #1473/#1724.

Rust, Go, JS/TS, Python, PHP and Ruby are unsupported on the axis, and that is the correct answer rather than an unfinished tranche: none of them filters on argument shape at all, so there is no existing check to factor, and building one would be exactly the query-layer overload solver the epic prohibits. An RQL author can bind reference occurrences and expand them into one mandatory overload-selection row plus one applicability row per candidate the production resolver considered, and can tell a uniquely resolved site from an ambiguous one, an exhausted overload set from a site nobody looked at, and a language that reports the axis from one that does not.

Six languages in, the pattern held without exception, and the reason is worth stating: every language already had the check, and every language had thrown the answer away in a slightly different place. Java threw it away in a `filter` closure; Kotlin in a boolean the walk called per unit; Scala inside a six-branch relation that collapsed every refusal into one value; C++ and C# in a second copy of the predicate that nothing forced to agree with the first. The factoring is always the same move -- make the refusing branch produce the reason, and let the boolean be that answer read as a boolean -- and it is always cheap, because the computation already existed.

The one thing that did *not* generalize is what an unrecorded parameter list means. Java falls back to counting the indexed signature, Kotlin and C++ treat it as undecidable, and C# refuses it against a defaulted zero. Those are three different language-side answers, and the rows report each one as its own resolver decided it rather than being normalized into a single story that would then disagree with some binding.

Two capability gaps are stated rather than approximated. Generic substitutions are absent from the applicability row because no resolver records a structured substitution map at its check, and an empty list would read as "none were needed". And the query-side rows are reachable only for a language that classifies `member_position` occurrences, which today means the axis is queryable for Java and pinned at the trace for Kotlin, Scala, C and C++ (#1473/#1724). Two per-language boundaries are recorded with their tranches: Scala publishes no callable record where the site writes no argument list at all, and C++ leaves a candidate its argument-type filter dropped unattributed on the callable axis.

Milestone 4 is complete. An RQLP author can now state the two things about a call site the relational plan could not express: that two ordered lists agree position by position, and that the callable the resolver selected is one its own applicability check accepted. Both are observable through `run_policy` over a real workspace: a Java call whose selected overload was refused by its own arity check is one finding at the call site, a Python call whose named arguments are written out of declaration order is one finding with parity zero, and the corrected fixtures of both are clean and provably non-vacuous.

The design lesson of this milestone is that lowering is a correctness property, not an economy. `assert-selected-in-winning-tier` produces the same join, group, aggregate and assertion an author could write by hand, so its findings, evidence, representative rows and completeness gating are the ones the relational path already proves; there was nothing new to test about how it reports, only about what it lowers to. The opposite case is `ordered-equal`, which genuinely could not be lowered -- no combination of equality joins and constant cardinalities compares two sequences position by position -- and it is the only thing in this milestone that touches the evaluator.

Two boundaries are stated rather than approximated. A strict cross-tier comparison is not expressible with equality joins and constant cardinalities, so the sugar states applicability-set membership and its description says so in those words. And whether an `ordered-equal` aggregate can see a length difference depends on the plan's join shape, not on the predicate; the docs say which join shape shows it and which one cannot.

Milestone 5 is complete. The issue's observable acceptance now runs: a seeded overload defect is one finding that names the call and both competing declarations, the corrected fixture is clean and provably non-vacuous, and a macro-derived argument list is unreliable rather than either. Human, JSON and SARIF describe that finding identically, down to the count of locations it carries.

Ten fixture families were planned. Eight are asserted as behavior, and the two that are not are boundaries with owners rather than omissions.

Asserted: same-total-arity overloads (Java factories at equal arity, and Scala curried versus flat lists at equal argument count -- the second is the family a flat arity integer genuinely cannot express); defaults and variadics as arity *ranges* (Java varargs query-side, C# defaults at the trace); named arguments as shape facts; curried and contextual calls (call shapes query-side, applicability at the Scala trace where five Milestone 3 tests already pin the refusals); constructors (Java, reachable through the `type_operand` occurrence of the type name); generic siblings by type-argument arity (C#, at the trace); method values (Java, `method_value` with the boundary that it claims no verdict); ambiguous factories (two equal winners retained); and macro-derived parameter lists (unknown coverage, zero fabricated rows, and the unreliable policy result).

Recorded as boundaries, not skipped:

- **Extractors.** No language ever produces `CallKind::Extractor`. Milestone 1 recorded this as a lowering gap: a Scala `unapply` pattern is not a call fact, and Scala's `instance_expression` is not in its kind table either. Nothing in this milestone can assert an extractor call kind without fabricating one. Closing it means adding kind-table entries, which changes what `query_code` returns for `kind: call` in Scala -- a separate visible change, owned by the Milestone 1 gap list.
- **Inherent-versus-trait precedence *with applicability*.** Rust performs no argument-shape filtering anywhere, and its member seams report both the inherent and the trait declaration at `dispatch_tier: trait_or_interface` with `applicability: unknown`, both selected. There is no precedence tier on the applicability row for Rust to expose and no verdict for it to state. The family is therefore asserted as what is real -- `supported: false`, `unknown_shape`, two undecided candidates, zero applicable and zero inapplicable -- and the fixture's comment says why reading that row set as "the inherent method won" would be reading a conclusion out of an absence. Giving Rust an argument-shape check would be the query-layer overload solver the epic prohibits; the axis stays unsupported by construction.

One boundary of the unreliable result is worth stating plainly, because a policy author can walk into it. The completeness signal lives on the mandatory `call_shape` row, so an exact-cardinality assertion over a call's arguments must *bind that row*. A plan that binds only the projected argument rows sees a legitimately empty set for a macro-derived site and concludes clean. This is the same shape as Milestone 4's join-shape caveat: what the assertion can see is a property of the plan, and the mandatory row exists to be bound. Making the projection itself emit a diagnostic for a suppressed shape would close it for every plan, but that changes `query_code` completion for ordinary queries too, so it belongs to the Milestone 6 review rather than here.

The design lesson of this milestone is about where a conformance sweep earns its cost. Six of the eight families confirmed behavior the earlier milestones already had. The two that did not were both the same failure mode -- an answer computed and then discarded one layer before anyone could read it -- and both were found by writing the fixture the plan asked for and watching it fail: C#'s generic-arity verdicts never reached the trace, and the applicability row had no identity to join a declaration by. ## Context and Orientation

Bifrost is a Rust workspace. `brokk-bifrost-core` contains dependency-bottom model types (`CodeUnit`, `Range`, `SignatureMetadata`, `CallableArity`, the `labelled_enum!` constrained vocabularies) and must not depend on another Bifrost crate. `brokk-bifrost-analysis` owns language analyzers, get-definition/usage resolution, and CodeQuery/RQL execution under `src/analyzer/structural/`. `brokk-bifrost-policy` owns RQLP parsing, the relational assertion plan, evaluation, findings, and rendering. MCP, LSP, the Python client, the VS Code extension (`editors/vscode/`), and published docs mirror visible query vocabulary.

A call site here is one exact call-shaped occurrence: a function/method call, constructor invocation, extractor/unapply pattern, infix application, operator application, or method-value/eta-expansion reference. A call shape is the complete ordered structure of that site: its call kind, its ordered argument-list groups (a Scala curried call has several; a Java call has one), each group's list kind (ordinary, type-arguments, named, contextual/implicit, block, receiver-bound, variadic pack), and each group's ordered arguments with optional names. A callable signature is the declaration-side counterpart read from the persisted `SignatureMetadata`/`CallableArity` contract. An applicability row relates one call site to one candidate callable with a verdict (`applicable`, `inapplicable`, `unknown`), a structured rejection reason when inapplicable, the substitutions the resolver used, the candidate's precedence tier, proof, and completeness.

The landed relational assertion plan (PR #1666) gives RQLP `bind`/`join`/`group`/`aggregate`/`assert` records over typed row fields; new row domains registered through `crates/bifrost-analysis/src/analyzer/structural/query/schema.rs` and `structural/search/results.rs` become bindable automatically once their fields enter the row-field registry. The `receiver-outcome`/`receiver-evidence` registrations are the model to follow.

## Validation and Acceptance

Every call site returns exactly one call-shape outcome row; argument group and argument rows are ordered, stably identified, and foreign-keyed; empty argument sets are distinguishable from unknown shapes by coverage. Signature rows come from the persisted contract and agree between cold and warm runs and between forward and inverse consumers. Applicability rows reproduce production selection exactly: the projected `applicable`-and-selected set equals the get-definition result for each fixture, losers stay visible with structured reasons, zero winners stay `unresolved`, multiple winners stay `ambiguous`. The final observable policy trio is: seeded bad overload -> `finding`; corrected -> `clean`; macro-derived shape -> `unreliable`.

## Idempotence and Recovery

All fixtures are temporary and every query/policy operation is read-only; re-running tests is safe. Schema additions are additive; old snapshots self-heal through existing version gates. If a language's matcher cannot be factored without behavior change, leave that language unsupported with an explicit capability entry and record the gap; do not approximate applicability with name or text matching. If a milestone fails after changing public row unions, repair every exhaustive consumer before proceeding.
